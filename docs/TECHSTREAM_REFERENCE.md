# Techstream reference evidence

> **Development priority #1:** before guessing further Toyota Data List identifiers,
> inspect the available Techstream 12.20.024 installation material and recover the
> actual IS220d read requests statically where possible. Runtime J2534 capture is
> the fallback, not the first step. This research task is separate from Flex's
> user-facing Techstream-reference import feature described below.

Status: **local, read-only external-evidence import for ECU Survey comparison; not a parser for Techstream proprietary files**.

## Why this layer exists

The project development study defines Techstream System Select / Health Check as the reference for installed ECUs, system state, DTC/FFD and calibration information. The same study requires ECU Survey topology to be compared against Techstream before previously unmapped responders are promoted into named vehicle-profile ECUs.

The currently available project material does not contain a stable Health Check export file format that Flex can safely implement as a proprietary-file parser. The Techstream Drive folder contains the installation archive, while the project maintenance evidence confirms that a real IS220d Health Check completed on 2026-09-06 and records several DTC observations. That is useful vehicle evidence, but it is not a complete machine-readable system inventory.

Flex therefore uses its own small neutral JSON evidence schema.

## Static Techstream research boundary

The **Flex app feature** below does not parse proprietary Techstream files. That
does not prevent repository development work from inspecting the locally supplied
Techstream installation material to identify read-only diagnostic definitions.

Static research may inspect database/configuration files and disassemble or trace
local DLL/EXE code paths to recover:

- target vehicle/profile selection keys;
- Data List item identifiers and units;
- diagnostic service and local identifier;
- 7E0/7E8 or other ECU addressing;
- response layout and conversion metadata;
- the bytes passed toward the J2534 write boundary.

Recovered information remains research evidence until independently checked
against the target vehicle. No static finding automatically changes the production
allowlist or marks a decoder vehicle-verified.

## Boundary

This feature:

- does not open or parse `.ddb` databases;
- does not parse or redistribute Techstream binaries, UI resources or internal databases;
- does not send anything to the vehicle;
- does not infer a CAN address from a Techstream system name;
- does not automatically identify an unmapped ECU;
- does not mark a mapping discrepancy as an ECU fault.

A reference can be transcribed from a Health Check, produced from screenshots during project review, or generated by another local research step. The imported JSON is evidence supplied to Flex, not a Techstream export claim.

## Schema v1

Top-level shape:

```json
{
  "schemaVersion": 1,
  "source": "techstream-health-check",
  "referenceId": "",
  "capturedAt": "",
  "note": "",
  "systems": [],
  "mappings": []
}
```

### `systems`

Each system is a presence observation from the external reference:

```json
{
  "name": "<system name transcribed from the reference>",
  "dtcs": ["C0215", "U0073"],
  "note": "<optional evidence note>"
}
```

Rules:

- system name is required;
- duplicate system names are rejected;
- DTCs use the usual `P/B/C/U` five-character form, with an optional hexadecimal suffix;
- no CAN address is derived from the name;
- the schema intentionally does not require or store a VIN.

### `mappings`

Mappings are optional and always explicit:

```json
{
  "requestHeader": "7E0",
  "responseHeader": "7E8",
  "systemName": "<exact name from systems[]>",
  "evidenceLevel": "candidate",
  "evidenceNote": "<why this mapping is being proposed>"
}
```

`evidenceLevel` is either:

- `candidate` — a research hypothesis; never counted as a verified ECU mapping;
- `verified` — a mapping backed by independently reviewed evidence recorded in `evidenceNote`.

The current survey request boundary remains `7E0`–`7E7`. A mapping outside that request plan is rejected by schema validation rather than silently extending survey coverage.

## Comparison behavior

`compareTechstreamReference()` compares only explicit mappings with the latest stored ECU Survey snapshot.

For each mapping it can report:

- `observed` — the mapped request header responded with the explicitly stated response header;
- `not-observed` — the survey node did not respond;
- `different-response` — the request header responded, but not with the explicitly stated response header;
- `outside-survey-plan` — defensive state for a mapping that cannot be associated with the supplied snapshot.

Overall comparison states include:

- `not-loaded`;
- `incomplete-reference`;
- `manual-review`;
- `verified-mappings-observed`;
- `verified-mapping-discrepancy`.

Even `verified-mappings-observed` is not an automatic release decision. The imported reference remains external evidence requiring human review.

## Unmapped evidence is preserved

Two independent lists remain visible:

- Flex responders without an explicit Techstream mapping;
- Techstream systems without an explicit CAN mapping.

Neither list is treated as a fault list. The IS220d has multiple network domains and equipment variants, so a one-to-one count is not assumed.

## Local storage and UI

The reference is stored separately from ECU Survey history under a versioned localStorage key.

The ECU Survey screen can:

- copy an empty neutral JSON template;
- import or replace a reference JSON;
- clear the reference;
- show systems and DTCs;
- show candidate/verified mappings and current survey observation state;
- show responders/systems that remain unmapped.

Importing or clearing a reference performs only a local re-comparison. It does not trigger a new diagnostic run or vehicle request.

## Report export

When a reference is loaded, the full ECU Survey text report appends a `TECHSTREAM REFERENCE` section containing:

- reference metadata;
- system and DTC counts;
- system/DTC list;
- explicit mapping evidence level and observation state;
- Flex responders without an explicit mapping;
- the interpretation boundary.

No Techstream proprietary raw file content or additional CAN/ELM transcript is added by this layer.

## Relationship to the 0.8.0 field-validation gate

The automatic three-run field-validation gate remains independent:

1. collect three same-build/same-state Flex runs;
2. satisfy the internal read-only validation checks;
3. reach `Valmis Techstream-vertailuun`;
4. load/review the Techstream reference separately;
5. only then decide whether the ECU Survey evidence is sufficient for a vehicle-validated release or a new ECU mapping PR.

A reference import does not automatically convert the field-validation gate into a 0.8.0 release approval.
